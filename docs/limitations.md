# Limitations

These are the things Pulse does not do, or does with known limits. This list comes from reading the code on `main`. If something here has been fixed, please open a pull request to update this page.

## Not supported

- **OpenTelemetry beyond agents.** The only OTLP receiver is `POST /v1/otel/v1/traces`, for LLM and agent spans ([AI agent observability](agent-observability-architecture.md)). No OTLP metrics or logs, and general service traces are not analysed.
- **Server SDKs.** None for Python, Java, Go, Ruby or Node for product events. Use plain [HTTP](integrations.md#server-side-events-over-http). (Agent tracing has its own SDKs in `sdks/ts-agent` and `sdks/py-agent`.)
- **Packaged mobile SDKs.** The iOS and Android core is beta and has to be built yourself ([mobile core](mobile-core.md)). React Native exists in `sdks/react-native` but is undocumented, untested in CI and not released.
- **Sign-in and identity.** No SSO/SAML, SCIM or MFA. No OAuth on the MCP endpoint, so OAuth-only MCP clients such as ChatGPT connectors cannot connect.
- **Email.** Pulse has no mailer. Verification and reset links are written to a local `outbox` file; invite links are returned to the admin who created them.
- **Not on registries.** The Web SDK is not on npm yet. Install it from the release `.tgz`.

## Data limitations

- **No time-based retention.** Data is kept until you erase a user or delete the storage. There is no TTL setting.
- **Erasure uses tombstones and event rows can stay in S3; agent data is physically purged before expiry.**
  - **Events and profiles (`erased_uids`):** Erased users are hidden at once across queries, profile reads, catalogs, and dead-letter inspection (`erased_uids` does not expire and hides rows with timestamp at or before the erasure time). In tiered S3 storage (`PULSE_HOT_STORE=local`), event segments are merged once at upload to `segments/` and at most once by cold S3 merge (`PULSE_COLD_MERGE_IDLE_SECS=3600`), so rows erased *after* that merge remain in S3 segment bytes indefinitely behind the tombstone, and external `distinct_id` strings remain in the local and S3 `identity/` snapshots. Exports and backups are not touched — operators with a legal duty to delete raw bytes must take this into account.
  - **AI agent traces (`agent_erasure_tombstones`):** Unlike `erased_uids`, agent erasure tombstones (`POST /v1/projects/:id/agent/erasure` or `DELETE /v1/projects/:id/agent/traces/:trace_id`) accept an optional `expires_at` (epoch ms) and are pruned from SQL once expired. Because of that expiry, Pulse physically purges and rewrites matching agent rows across L0, `agent_wal/`, local `hot/agent_segments/`, S3 `agent_segments/`, `agent_published/`, and `pending_gc` / `pending_s3_deletes` **before** `expires_at` expires (and refuses to prune a tombstone from SQL or stop enforcing it until `physically_purged_at_ms` is recorded). Note that `agent_wal_corrupt/` quarantine files and curated SQL evaluation/dataset/alert artifacts (`agent_dataset_items`, `agent_experiment_runs`, `agent_alert_events`) are not rewritten by trace erasure.
- **Schema caps.** At most 8,192 event names and 16,384 property keys per project. On `/v1/ingest`, per-request `422` caps are not enforced; events that exceed the per-project cap are dead-lettered by the background processor instead of blocking the project. Sync bulk `/import` still rejects schema-cap overflows with `422`.
- **Size limits.** Event and property names: 255 characters. String values are truncated to 8 KiB. Request body: 8 MiB.
- **Dead-lettered events.** An event that cannot be turned into a row after its write-ahead-log record is durable (e.g. the project's dictionary or schema cap is full) is written to `wal_dead/<project>/bucket_NNN/seq_<n>_<fingerprint>.plsd` (`<data_dir>/wal/wal_dead/` under `PULSE_HOT_STORE=local`, or object store under `object`) with its timestamp and refusal reason, and skipped. Inspect them with `pulse-node dead-letters --project-id <id>` (which automatically filters out erased users). Legacy `.plsb` files remain readable.
- **Accepted is asynchronous up to the writer flush bound (`20 ms` / `1 MiB`) and not instantly queryable on other nodes.** `/v1/ingest` acknowledges `200` once queued in the bounded writer memory buffer (`deduped` is always `0` in the response; exact duplicates are reported in `pulse_ingest_events_deduped_total`). A sudden `SIGKILL` / power loss can drop at most the un-WALed buffer window (default `<= 20 ms` or `<= 1 MiB`); clean shutdown (`SIGTERM`) drains 100% of buffered events to WAL and L1 before exit. On the same node, queries wait up to 250 ms (`open_for_read`) for logged events to be applied to L0; if the processor is further behind, the query runs on what has been applied so far. Remote `query` nodes see data after the next publish cycle (`PULSE_UPLOAD_INTERVAL_SECS`).
- **Agent trace size.** One request may carry at most 512 spans per trace. Across requests, a trace accepts 10,000 span records or about 64 MiB (estimated in-memory size), whichever comes first; later spans are dropped, reported in the response's `dropped_spans` and counted in `pulse_agent_spans_dropped_trace_limit_total`. A span sent as start, update and final counts three times. The counts are kept in memory per node and reset on restart.
- **Dedup windows.** `/v1/ingest` deduplicates within 15–30 minutes only. A retry after that is counted again (`/import` remembers ids for 30 days).
- **Changing bucket count.** Do not change `PULSE_NUM_BUCKETS` on a data directory that already has data. Events route by `hash % num_buckets`, so changing it would split one user's history across buckets. This is inferred from the routing code; migration is not documented.
- **Two organisation tables.** `orgs` and `organizations` both exist in the metadata DB. This matters only if you query the DB directly.

## Query limitations

| Limit | Value |
|---|---|
| Query timeout | 30 s (`PULSE_QUERY_TIMEOUT_MS`) |
| Rows scanned per query | 250 M (`PULSE_QUERY_MAX_ROWS`) |
| Memory per query | 1 GiB (`PULSE_QUERY_MAX_MEMORY_MB`) |
| Time buckets per insights query | 10,000 |
| Breakdown groups (insights, funnels) | 250 |
| Retention cohorts | 10,000 |
| Flows: events scanned / per user | 2,000,000 / 4,096 |
| Nested cohort depth | 32 |
| Event export | 50,000 events per call |

- **Sampling.** Queries over 10 M estimated rows are sampled by default (`auto`). Sampled results are disclosed and can be forced exact.
- **HLL estimates.** Long-range unfiltered uniques use HyperLogLog sketches with about 3 % error.
- **No SQL.** The query API is structured JSON (insights, funnel, retention, flows). Custom properties use SQL expressions internally, but you cannot run arbitrary SQL over events.

## Experiments (on `main`)

- **Peeking.** Significance is a fixed-horizon two-proportion z-test with Holm-Bonferroni correction. Repeatedly checking a running experiment inflates false positives. Sequential testing is in review in separate pull requests.
- **Metrics.** Experiment metrics are conversion rates only. Count, sum and ratio metrics are not on `main`.
- **Variant stability.** Assignment hashes the current distinct id, so `identify()` can change a user's variant.

## Operational limitations

- **One owning storage node per project; stateless `writer` and `query` scale horizontally.** Each project has one authoritative owner in `project_owner` (`ingest` or `all`). Multiple stateless `--role writer` nodes can accept async `/v1/ingest`, `/v1/agent/traces`, and `/v1/otel/v1/traces` for any project (`writer_log/` `PWLF` v2 → async idempotent forward to the project's owner) and route sync/query calls, and multiple `--role query` nodes can read S3 `published/` + `agent_published/` and forward storage-writing mutations to the owner. Non-owner `ingest`/`all` nodes reject unforwarded async ingest with `503 not_owner` and forward sync/query/admin calls to the owner.
- **Per-node state.** The ingest rate limit, login lockout, in-memory event dedup windows (when scaling multiple `writer`s for a project, event dedup runs at the owner and agent traces deduplicate by `(writer_id, offset)` in `writer_offsets` across `T_expire = 7d`), and OAuth state are kept in memory per node. With several nodes, rate limits apply per node, and an OAuth flow must return to the node that started it.
- **The hot tier (WAL, identity, profiles, manifests, `hot/segments/`, `hot/agent_segments/`, `hot/replay/`, and `agent_manifests/`) is on local disk by default.** With `PULSE_HOT_STORE=local`, acknowledged events and traces are fsynced to `<data_dir>/wal` (`wal/`, `wal_corrupt/`, `wal_dead/`, `agent_wal/`, `agent_wal_corrupt/`), L0-flushed event and agent segments are written to `<data_dir>/hot/hot/segments/` and `<data_dir>/hot/hot/agent_segments/`, session-replay chunks and cursors stage in `<data_dir>/hot/hot/replay/` and `<data_dir>/hot/hot/replay_cursors/`, and the SlateDB identity graph (`identity/`), profile store (`profiles/`), and authoritative event and agent manifests (`manifests/`, `agent_manifests/`) are fsynced to `<data_dir>/hot` (including multipart uploads), so request acknowledgement and normal L0 flushes make zero calls to S3 `segments/`, `published/`, `replays/`, `agent_segments/`, or `agent_published/`. Every `PULSE_UPLOAD_INTERVAL_SECS` (default `300`, `0` = eager) and on clean shutdown, a 7-step upload cycle freezes eligible local event segments (closed dates `date < today_utc` upload on a 1 h timer or immediately above `4 MiB`), snapshots profiles and identity (`T_id >= T_prof >= T_freeze`), merges frozen event segments per `(date, bucket)` up to `64 MiB` input bytes into create-only S3 `segments/`, commits the local manifest, writes a create-only S3 `PublishedManifest` at dense `publish_seq`, and deletes unpinned local segments; the cycle also uploads pending `hot/replay/` chunks to S3 `replays/` (with `copy_if_not_exists` and sequence-shift recovery on `AlreadyExists`), and runs the same local-to-S3 merge/publish cycle for `hot/agent_segments/` -> `agent_segments/` and `agent_manifests/` -> `agent_published/`. Cold S3 merge (`PULSE_COLD_MERGE_IDLE_SECS=3600`) consolidates closed-date multi-segment S3 partitions once idle; truly idle projects (and projects holding only deferred closed-date segments) make **zero** S3 calls across event, replay, and agent maintenance loops. Superseded S3 segments and S3 snapshot blobs are retained under a persisted 2-publish-interval deletion grace rule (and while locally pinned; finite-TTL agent erasures accelerate deletion strictly before `expires_at_ms`). Local `hot/segments/` bytes are bounded by `PULSE_HOT_SEGMENTS_PROJECT_MAX_MB` / `PULSE_HOT_SEGMENTS_MAX_MB` (`512` / `2048` MiB `1x`): crossing `1x` triggers an early upload (with cooldown), and if S3 stays unreachable until `2x`, `/v1/ingest` returns HTTP `429` (`hot_segment_backpressure`). On write-open, the node validates dense `publish_seq`, `writer_generation`, and `source_local_epoch` against S3 `published/` and `agent_published/` (refusing stale/deposed writers while recovering step-6 self-crashes cleanly), replays any `upload_intent.json` to clean up orphaned S3 objects, sweeps unreferenced local `hot/segments/` and `hot/agent_segments/` files, and fails closed (`503`) if S3 is unreachable while seeding dedup from recent S3 segments. A process crash loses nothing: the WAL is replayed and local SlateDB/manifest state recovers on restart. Losing the `<data_dir>` volume causes an outage rather than silent UID reuse: `<data_dir>/hot_store_mode` records the initialized mode, and writable nodes refuse to start if the mode mismatches `PULSE_HOT_STORE`, if opposite-tier hot objects exist, or if `local` mode's `<data_dir>/hot/identity`, `<data_dir>/hot/profiles`, or `<data_dir>/hot/manifests` store is missing or wiped while `published/`, `agent_published/`, or other project state exists. To recover a wiped `<data_dir>` from the latest S3 `published/` and `agent_published/` snapshots, run `pulse-node restore --from-published --data-dir <path>` explicitly — this requires an external PostgreSQL `DATABASE_URL` (SQLite `pulse_meta.db` is refused by `restore --from-published` because accounts, projects, and `erased_uids` tombstones on SQLite are lost with the volume, and `PULSE_HOT_STORE=local` logs a startup warning when running on SQLite) and loses any events, agent traces, profile updates, identity merges, and erasures after the printed publish timestamp. Put `<data_dir>` on a persistent volume, not on an instance's ephemeral disk. A full disk or unwritable `wal/` or `hot/` directory answers `503` and acknowledges nothing. Running more than one ingest-capable machine for a project (a node that may take over the lease) requires `PULSE_HOT_STORE=object` or a `<data_dir>` on a shared volume: otherwise the machine taking over cannot see the hot state the previous one left. Switching an initialized data directory between `local` and `object` is refused at startup. A remote `query`-role node on another machine starts with an empty `<data_dir>`, reads S3 `published/` and `agent_published/` manifests, restores Candidate B identity and profile snapshots locally into `<data_dir>/query_hot`, reads S3 `segments/`, `agent_segments/`, and both local/S3 `replays/`, and filters `erased_uids` and `agent_erasure_tombstones` live from external Postgres — seeing data up to `PULSE_UPLOAD_INTERVAL_SECS` old (while a `compactor`-role node has nothing to compact across machines in `local` mode when `manifests/` and `hot/segments/` are local and `PULSE_UPLOAD_INTERVAL_SECS > 0`).
- **A second ingest node for the same project is refused safely; standby failover requires `PULSE_HOT_STORE=object` or shared `<data_dir>`.** Each project's storage has one active `project_owner` and lease holder at a time in the metadata database. A non-owner or lease-less `ingest` or `all` node answers `503` (`code: "not_owner"` or `"not_writer"`) on unforwarded async ingest rather than overwriting the active owner's events; stateless `--role writer` nodes buffer to `writer_log/` and wait for the owner to come back or ownership to transfer. Other consequences of the lease: after a crash, the restarted node waits out its old lease before it accepts events for the projects it held; when the metadata database is unreachable for longer than two thirds of the TTL, ingest stops until it is back; node clocks must agree to within a third of the TTL. The lease covers events, identity, user profiles and the WAL. In `PULSE_HOT_STORE=local` mode, replay chunks stage locally in `hot/replay/` and upload on the lease-holding writer's cycle (`replays/` via `copy_if_not_exists` + `AlreadyExists` sequence shift), and agent segments/manifests (`hot/agent_segments/`, `agent_manifests/`) use the local hot tier + cycle upload/publish (`agent_published/` create-only dense `publish_seq` fencing); under `PULSE_HOT_STORE=object`, agent traces use per-process writer ids and replay chunks use create-only `replays/` objects directly.
- **TLS.** No built-in TLS for HTTP. Use a reverse proxy. QUIC uses a self-signed certificate.
- **Encryption.** Event data is encrypted at rest only if you set `PULSE_BYOK_MASTER_KEY`. A passphrase is stretched with a fixed salt. Whether rotated keys survive a restart is not verified.
- **Google sign-in.** The id_token signature is not verified; Pulse relies on the TLS exchange with Google's token endpoint.
- **Performance numbers.** The figures in the README come from one machine and synthetic data. No production-hardware benchmarks are published.

## Platform support

- **Release binaries.** Linux x86_64 and aarch64 with glibc 2.35+ (Ubuntu 22.04+, Debian 12+), plus a multi-arch Docker image. No macOS or Windows binaries; build from source there.
- **Releases lag `main`.** These docs describe `main`. A feature merged after the latest release (listed under *Unreleased* in the [changelog](../CHANGELOG.md)) needs a source build until the next release.
- **Rust toolchain.** Pinned to 1.88 (`rust-toolchain.toml`).
